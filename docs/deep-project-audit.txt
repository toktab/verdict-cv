EXECUTIVE VERDICT

This project is a serious full-stack app, not just a toy demo. It has a Spring Boot backend, React/Vite frontend, MySQL schema with Flyway migrations, auth/session/admin flows, candidate/project/hiring workflow, audit/claim-verification engine, LLM integration with fallback, candidate scoring and analysis history, SignalTrace/OSINT concept, messaging/team/invites/announcements, Docker deployment, backend integration tests, and frontend Playwright smoke tests.

It also has strong signs of a hackathon/prototype that grew quickly: branding and architecture drift, stale TODO docs, large frontend files, large backend services, inconsistent naming, partial OSINT implementation, compliance risk around hiring automation, fragile frontend state management, custom security that should be hardened, and several features implemented in UI before being fully trustworthy operationally.

Recommended strategy: do not rewrite it. Stabilize the product truth, separate domains, harden security/compliance, and simplify frontend state/routing.

2. PRODUCT ASSESSMENT

The product is VERDICT, a hiring intelligence and claim-audit system.

It lets a hiring team:
1. Create a hiring project/job.
2. Add candidate CVs/resumes.
3. Extract claims.
4. Score candidate-job match.
5. Flag unsupported, stretched, or risky claims.
6. Run local or AI-backed audit.
7. Produce match reports.
8. Collaborate with team members.
9. Run consent-based public evidence checks called SignalTrace.
10. Export evidence/audit reports.

The strongest product direction is: VERDICT: CV and candidate evidence verification for hiring teams.

The project still contains two identities:
1. Generic claim audit platform.
2. Hiring/CV verification ATS platform.

Recommendation: keep the generic audit engine internally, but make the hiring/CV verification workflow the public product.

3. FRONTEND AUDIT

What is good:
- Rich feature coverage: landing, auth, dashboard, projects, candidates, reports, messages, admin, audit workspace.
- Strong UX concepts: state comparison, candidate scoring, ATS reports, evidence cards, reviewer notes, votes, SignalTrace, Georgian/English translation.
- api.js centralizes API calls.
- navigation.js has explicit route mapping.

Main frontend problems:

Problem 1: App.jsx is too big and too responsible.
It owns routing, auth state, project state, audit state, upload logic, realtime, notifications, header, layout, and route rendering.

Improve by splitting into:
- src/app/AppShell.jsx
- src/app/AppRoutes.jsx
- src/app/useAuthSession.js
- src/app/useProjects.js
- src/app/useAuditWorkspace.js
- src/app/useRealtime.js
- src/app/Header.jsx
- src/app/RouteLoadingFallback.jsx

Problem 2: Manual routing instead of React Router.
The app uses route names and window.history.pushState. This creates risks around back/forward, refresh, nested layouts, route params, auth guards, and loading states.

Improve by moving to React Router routes with route params.

Problem 3: Global state is passed everywhere.
Many pages receive projects, projectsLoading, onProjectsChange, user, userToken, setUser, setUserToken, setRoute, navigateTo, Header, Metric.

Improve with hooks/context:
- useAuth
- useProjects
- useNavigation
- useToast
- useCurrentProject
- useCurrentCandidate

Problem 4: api.js is one large file.
It includes auth, projects, candidates, messages, realtime, admin, normalizers.

Improve by splitting into:
- src/api/http.js
- src/api/authApi.js
- src/api/projectApi.js
- src/api/candidateApi.js
- src/api/messageApi.js
- src/api/adminApi.js
- src/api/auditApi.js
- src/api/realtimeApi.js
- src/api/normalizers.js

Problem 5: Browser-readable session tokens.
If tokens are in localStorage/sessionStorage, XSS can steal them.

Production improvement:
- HttpOnly Secure SameSite cookies for refresh/session, or short-lived in-memory access tokens.
- Rotate refresh tokens.
- Add CSRF protection if cookie-based auth is used.

Problem 6: Some UI appears ahead of backend reality.
SignalTrace UI is broader than backend. Profiling mode started as demo/highlight mode. Admin/profile/audit internals may still have legacy pieces.

Improve with a feature matrix and hide or label incomplete features.

Problem 7: Accessibility needs automated validation.
Good signs exist, like DialogKeyboardManager and smoke checklist keyboard checks, but add axe-core Playwright tests, focus snapshots, semantic landmarks, and aria-live for async status.

4. BACKEND AUDIT

What is good:
- Clear package separation.
- DTO records are used.
- Flyway migrations with ddl-auto=validate.
- LLM fallback through StateAnalysisOrchestrator.
- Audit history preservation in V28.

Main backend problems:

Problem 1: HiringService is too large and does too much.
It handles project creation/listing, candidate creation/upload, PDF/DOCX parsing, scoring, OSINT, GitHub API calls, messages, activity logging, permissions, memory, audit integration, realtime publishing.

Improve by splitting into:
- HiringProjectService
- CandidateIntakeService
- CandidateAnalysisService
- CandidateScoringService
- CandidateOsintService
- CandidateWorkflowService
- ProjectInviteService
- ProjectMemberService
- GithubEvidenceService
- ResumeTextExtractionService
- DemoWorkspaceSeeder

Problem 2: HiringController is too broad.
It exposes projects, settings, activity, announcements, ATS templates, permissions, candidates, uploads, workflow, notes, votes, invites, members, OSINT.

Improve by splitting controllers:
- ProjectController
- ProjectSettingsController
- ProjectTeamController
- ProjectAnnouncementController
- CandidateController
- CandidateReviewController
- CandidateSignalTraceController

Problem 3: Custom auth/security needs hardening.
SecurityConfig disables CSRF and uses stateless bearer-style auth. /api/admin/** is permitAll at Spring level and likely protected by AdminAuthFilter manually.

Risks:
- Custom filters are easy to get wrong.
- JS-readable tokens increase XSS impact.
- Query token support can leak tokens into logs/history.

Improve by:
- Prefer Spring Security auth mechanisms where possible.
- Require admin auth at Spring authorization level too.
- Avoid query tokens except short-lived realtime tickets.
- Hash tokens in DB if not already.
- Add security tests for admin/user/expired/deleted/CORS cases.

Problem 4: Permission model is string-based.
Permissions like canView, canVote, canAddNote can drift between frontend and backend. Role parsing uses text matching.

Improve with enums:
- ProjectRole
- ProjectPermission

Problem 5: LLM integration is practical but basic.
Good: timeout, retry, cost tracking, fallback, schema tests.
Weak: generic JSON response format, blocking retry sleep, no circuit breaker, no per-user/project budget guard, prompt injection protections unclear.

Improve with strict structured outputs, budget limits, input truncation warnings, golden-set evals, and human review gates.

Problem 6: SignalTrace/OSINT is legally sensitive.
The UI has GitHub, LinkedIn, socials, personal sites, certificates, identity scans. Docs correctly warn not to scrape LinkedIn and to use consented evidence.

Improve with strict consent workflow:
- Candidate consent record required.
- Scope of checks stored.
- Public-source URLs stored.
- Evidence source and timestamp stored.
- No scraping restricted sites.
- Candidate appeal/correction.
- Job-relevance filter.
- Retention policy.
- Audit log for every external lookup.

Problem 7: Error handling should log internally.
GlobalExceptionHandler returns safe messages, which is good. Ensure internal logs include exception class, request ID, route, actor, and stack trace.

Examples:

- audit_phrase_matches_json

Improve by keeping JSON snapshots for reports, but normalizing operational data into tables such as candidate_claims and candidate_public_sources.

Problem 2: Schema naming drift.
Old TODO docs mention app_user, hiring_project, project_candidate, FastAPI, Alembic. Current code uses user_accounts, hiring_projects, hiring_candidates, Spring, Flyway.

Improve by archiving or rewriting stale docs.

Problem 3: User deletion and uniqueness.
Soft-deleted users still have unique username/email. Decide whether email reuse is forbidden forever, anonymized on delete, or restored.

Problem 4: Deletion policy needs documentation.
Create a deletion/retention matrix for projects, candidates, audits, notes, messages, analysis runs, and OSINT evidence.

9. SECURITY AND COMPLIANCE AUDIT

Main risks:

1. Automated hiring score risk.
Scores can influence hiring. Add disclaimers and workflow constraints:
- Decision support only.
- Human review required.
- Do not reject solely based on automated score.
- Candidate can provide correction/evidence.
- Score explanation required.

2. OSINT/privacy risk.
Add consent record, source scope, retention period, source allowlist, no scraping restricted sites, candidate appeal, and audit logs.

3. Bias risk.
GitHub activity can bias against people with private work or non-open-source backgrounds. Missing GitHub should not heavily penalize by default.

4. Token/session risk.
JS-readable tokens are acceptable for prototype, but production should use secure cookie or in-memory token model.

FINAL SUMMARY

This is a strong, ambitious hiring verification product. The backend is real, the database is real, and the frontend is feature-rich. The main problem is not lack of features. The main problem is that it grew too fast: big files, mixed old/new concepts, custom security, stale docs, and sensitive OSINT/hiring compliance risk.

To make it better, do not rewrite it. First make the product scope clear, then split oversized frontend/backend files, harden permissions and consent, normalize the most important data, and add tests around security, SignalTrace, and candidate scoring.
