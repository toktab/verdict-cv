================================================================================
                    VERDICT CMD CONNECTOR BLUEPRINT
================================================================================

Purpose
-------
Create a Windows command-line connector for the VERDICT website. The connector
must let a signed-in user perform the important website workflows from CMD,
PowerShell, Windows Terminal, CI jobs, and scripts without replacing the site.

Suggested executable names:

  verdict
  verdict-cli

Preferred name throughout this document:

  verdict

Implementation status (2026-07-17)
----------------------------------
The connector is implemented in tools/verdict-cli/verdict.mjs with the root
verdict.cmd launcher. It includes one-command, interactive shell, dashboard,
realtime SSE, structured output, encrypted credential storage, guarded
destructive operations, admin tooling, batch workflows, and website deep links.

The website Profile page also lists every CMD login with connector name, IP,
user agent, first/last access, active state, and an immediate revoke action.

Runnable examples and installation steps are in tools/verdict-cli/README.txt.
Automated CLI checks are in tools/verdict-cli/verdict.test.mjs.


================================================================================
1. PRODUCT GOALS
================================================================================

The connector should:

1. Connect to a local or hosted VERDICT server.
2. Authenticate securely without exposing passwords or tokens in command history.
3. Make projects, candidates, audits, messages, teams, templates, reports, and
   health information available from the terminal.
4. Support both human-readable output and stable JSON output for automation.
5. Stream realtime events instead of requiring repeated refresh commands.
6. Make destructive actions difficult to perform accidentally.
7. Respect exactly the same backend permissions as the website.
8. Open the relevant website page when a workflow is better completed visually.
9. Work well from plain cmd.exe, PowerShell, Windows Terminal, and CI runners.
10. Never create a separate source of truth. The server remains authoritative.

The connector should not:

- Reimplement candidate scoring locally.
- Store projects, messages, votes, or permissions as authoritative local data.
- Bypass backend permissions.
- Silently scrape private websites.
- Put passwords or long-lived tokens directly into command arguments.
- perform destructive actions without confirmation.


================================================================================
2. THREE USAGE MODES
================================================================================

A. One-command mode

  verdict projects list
  verdict candidate show --project 12 --candidate 44
  verdict messages send --to reviewer --subject "Review" --body "Please check 44"

Best for quick actions and scripts.

B. Interactive shell mode

  verdict shell

Example prompt:

  VERDICT [local / toko1] > projects
  VERDICT [local / toko1] > use project 12
  VERDICT [project 12]    > candidates
  VERDICT [project 12]    > use candidate 44
  VERDICT [candidate 44]  > audit run

The shell remembers the selected project and candidate for the current session.
It should provide command completion, command history, help, and safe prompts.

C. Watch/dashboard mode

  verdict watch
  verdict watch messages
  verdict watch project 12
  verdict dashboard

Watch mode streams Server-Sent Events and prints new messages, audit completion,
project deletion, invite acceptance, and team changes in real time.

================================================================================
4. GLOBAL COMMAND SYNTAX
================================================================================

General grammar:

  verdict [global-options] <resource> <action> [arguments] [options]

Global options:

  --profile <name>       Select local, staging, production, or another profile.
  --server <url>         Override the configured server for this command.
  --output <format>      table, json, jsonl, csv, text, or quiet.
  --fields <list>        Select fields for table/CSV output.
  --no-color             Disable ANSI colors.
  --no-headers           Hide table headers.
  --page <number>        Select a server page.
  --size <number>        Select page size, capped by the server.
  --search <text>        Search the selected resource.
  --timeout <seconds>    Override request timeout.
  --request-id <id>      Supply a traceable request ID.
  --yes                  Accept ordinary confirmations, never critical phrases.
  --dry-run              Show what would happen without changing the server.
  --verbose              Show request timing and extra diagnostic information.
  --debug                Show HTTP details with credentials redacted.
  --help                 Display contextual help.
  --version              Display CLI and compatible server versions.

Examples:

  verdict projects list --search backend --page 1 --size 20
  verdict projects list --output json
  verdict messages list --folder inbox --fields id,from,subject,createdAt
  verdict --profile production health

5. AUTHENTICATION AND SESSION COMMANDS
================================================================================

Commands:

  verdict login
  verdict login --user toko1
  verdict login --browser
  verdict logout
  verdict logout --all
  verdict whoami
  verdict session status
  verdict session refresh
  verdict session clear

Login flow:

1. Prompt for username/email if omitted.
2. Prompt for password with hidden input.
3. Call the normal VERDICT login API.
4. Store the session token in Windows Credential Manager when available.
5. Store only non-secret profile settings in the config file.
6. Print the signed-in name, username, role, server, and session expiry.

Example output:

  Signed in
  Name       Toko Tabagari
  Username   toko1
  Role       Analyst
  Server     http://localhost:8080
  Profile    local

Authentication errors should say:

  Authentication failed: your session is missing, expired, or invalid.
  Run `verdict login` and try again.

The connector must never trigger a browser Basic Authentication popup. It should
always use the same Bearer-token contract as the website.

================================================================================
17. TERMINAL VISUAL DESIGN
================================================================================

Visual principles:

- Quiet, dense, work-focused interface matching VERDICT.
- Black/charcoal base when the terminal supports color.
- Red for primary actions and destructive warnings.
- Green for verified/supported/success.
- Amber for stretched/warning/pending.
- White/light gray for ordinary text.
- Never depend on color alone.
- Avoid huge ASCII logos on every command.
- Keep columns aligned and truncate safely with an ellipsis marker.

Small startup mark for interactive mode:

  VERDICT CLI
  Confidence is not evidence.

Table behavior:

- Detect terminal width.
- Hide optional columns on narrow windows.
- Provide `--wide` to show all columns.
- Provide `--wrap` to wrap descriptions.
- Pipe-safe output automatically disables animation and color.
- Long results open in an internal pager or the configured pager.

Progress design:

  Uploading nino.pdf       [########------] 58%  4.6 MB/s

Spinner animation must stop when output is redirected to a file.

Accessibility:

- Respect NO_COLOR.
- Support high-contrast palettes.
- Offer `--no-unicode` for older CMD encodings.
- Use text labels with every status icon.
- Avoid rapidly updating the screen in reduced-motion mode.

- Data goes to stdout.

  2   Invalid arguments or malformed input
  3   Authentication required or session expired
  4   Permission denied
  5   Resource not found or deleted
  6   Conflict or invalid state transition

================================================================================
20. SAFETY AND CONFIRMATION MODEL
================================================================================

Level 0 - Read only

No confirmation: list, show, search, health, export to a new file.

Level 1 - Reversible ordinary change

Usually no prompt when all arguments are explicit: mark read, star, archive,
post a note, change notification preference.

Level 2 - Important team/workflow change

Require Yes/No unless `--yes`: send external message, invite, role change,
candidate lifecycle transition, announcement deletion.

Level 3 - Destructive or ownership change

Always show impact and require typed confirmation: project deletion, candidate
deletion, team kick, Head Admin transfer, admin user deletion, table clearing.
`--yes` cannot bypass typed confirmation.

Dry run:

  verdict team kick --project 12 --user reviewer --dry-run

Example:

  WOULD REMOVE
  User       reviewer@example.com
  Project    #12 Java Backend Developer
  Role       Reviewer
  Effects    Access revoked; action written to project history


================================================================================
21. SECURITY MODEL
================================================================================

Requirements:

- Store session secrets in Windows Credential Manager where possible.
- Fall back to an encrypted user-scoped credential file, never plain text.
- Restrict config/credential files to the current Windows user.
- Redact Authorization, X-Admin-Token, passwords, API keys, and cookies in logs.
- Do not accept passwords on command arguments by default.
- Keep normal user and admin sessions separate.
- Validate HTTPS for remote servers.
- Warn before sending credentials to plain HTTP on a non-local address.
- Allow `http://localhost` and `http://127.0.0.1` for local development.
- Defend against malicious filenames and terminal escape sequences in server data.
- Normalize and validate output paths.
- Use backend permissions for every operation.
- Expire cached sessions when the server returns 401/403.
- Provide `verdict session clear` for lost/shared machines.

Possible later improvement:

- Device-code login in a browser, so the CLI never handles the password.
- Scoped personal access tokens with read/write/admin capabilities.
- Token revocation list visible in the website profile.

================================================================================
25. OFFLINE AND FAILURE BEHAVIOR
================================================================================

The first version should not offer offline writes. When the server is unavailable:

- Read commands may display a clearly labeled recent cache if requested.
- Write commands fail without pretending they succeeded.
- A retry command can reuse the safely stored request body.
- Passwords, CV contents, messages, and OSINT evidence are not cached by default.

Options:

  --no-cache
  --cache-ttl 5m
  --retry 3
  --retry-delay 2s

Retries:

- Retry safe GET requests automatically for transient network errors.
- Retry writes only when an idempotency key/request ID is supported.
- Never duplicate message sends, invites, audits, notes, or candidate uploads.

  for %f in (C:\CVs\*.pdf) do verdict candidates upload --project 12 --file "%f"

Export projects to JSON:

  verdict projects list --output json > projects.json

Wait for an audit and branch on result:

  verdict audits watch 481 --output quiet
  if errorlevel 1 echo Audit failed

PowerShell pipeline:

  verdict candidates list --project 12 --output json |
    ConvertFrom-Json |
    Where-Object { $_.score -ge 80 }

Future batch file:

  verdict batch run workflow.json

Potential workflow operations:

- Create project
- Upload a directory of CVs
- Wait for analyses
- Export comparison report
- Message selected reviewers

Batch mode needs validation, dry-run, per-step results, and stop/continue policy.

28. PROPOSED INTERNAL ARCHITECTURE
================================================================================

Logical modules:

  command-parser
      Parses arguments, aliases, options, and contextual help.

  profile-config
      Reads non-secret profiles and resolves environment overrides.

  credential-store
      Integrates with Windows Credential Manager and session expiry.

  api-client
      Handles REST requests, authentication, timeouts, request IDs, and errors.

  realtime-client
      Handles SSE connection, reconnect, filtering, and deduplication.

  resource-services
      Auth, projects, candidates, messages, audits, teams, ATS, admin.

  presenters
      Table, text, JSON, JSONL, CSV, progress, and error output.

  confirmations
      Central safety levels, impact previews, countdowns, and typed phrases.

  file-service
      Upload validation, safe paths, downloads, and non-overwrite behavior.

  shell
      Interactive context, completion, history, and prompt rendering.

  diagnostics
      Doctor, health, version compatibility, and redacted debug logs.

Important rule:

Commands must call service interfaces. Commands should not construct raw HTTP
requests themselves. This keeps human mode, JSON mode, and interactive mode on
the same tested behavior.


================================================================================
29. VERSIONING AND COMPATIBILITY
================================================================================

Commands:

  verdict version
  verdict version --server

Output:

  CLI version       1.0.0
  Server version    0.0.1
  Server commit     abc1234
  API compatibility compatible

The server health/version response should eventually expose an API version.

Rules:

- Patch CLI versions may change human formatting.
- Minor versions may add commands and JSON fields.
- Major versions may change command or JSON contracts.
- The CLI must warn before using an unsupported server version.
- Destructive commands should refuse to run on unknown incompatible versions.

================================================================================
34. DEFINITION OF DONE
================================================================================

The connector is ready for normal use when:

- Installation and PATH setup work on a clean Windows machine.
- Login never exposes a password or token.
- All commands respect backend permissions.
- Human, JSON, JSONL, and CSV outputs are deterministic and documented.
- Project/candidate/message/audit changes appear on the website immediately.
- Website changes appear in CLI watch mode immediately.
- Destructive actions provide impact previews and cannot be bypassed casually.
- A disconnected or expired session produces a clear recovery command.
- Plain CMD output remains readable without Unicode or color.
- File uploads validate limits before sending.
- Errors map to stable exit codes.
- Logs redact every credential.
- Critical workflows have integration tests with two user accounts.
- CLI and server versions report compatibility.
- `verdict doctor` can explain the most common setup failures.
